0.1 项目是什么

一个跑在华为鸿蒙手表上的 DeepSeek 客户端，纯原生 ArkTS 实现， 直接调用 DeepSeek 官方 Web API，不套壳、不加载网页。

屏幕 466 × 466 圆形

设备型号 HUAWEI WATCH 5 / RTS-AL00
开发语言 ArkTS（ArkUI 声明式）

0.2 这份教程的独特之处

市面教程大多停留在"新建工程 → 点运行"。这份不同——它记录的是 一个真实项目从编译失败到真机跑通的全过程，包括：

  • 华为设备签名为什么必须走官方通道（自签名装不上）
  • 手表 IP 变了怎么找回来（端口反查法）
  • 官方输入法是全屏模式，如何在这种约束下设计交互
  • 圆屏为什么总"显示不全"，以及几何层面的解法
  • token 取值路径写错导致的"登录失败"如何定位
  • 逆向 DeepSeek 的 PoW 算法：三处错误让消息根本进不了服务端
  • SSE 格式对不上：消息进了服务端，界面却一片空白
  • 手表主线程算 6 秒就被系统杀：THREAD_BLOCK_6S 与 taskpool 解法
  • 没有单步调试时，怎么用 hilog + dumpLayout 验证真机行为
  • AI 是怎么操控电脑上的 DevEco Studio 完成这些操作的

第 3 章 · 手表端开发（核心）

3.1 圆形屏：最大的设计约束

手表不像手机是矩形，它是圆形。屏幕四角不存在， 内容排到边缘就会被圆弧切掉。

本项目把圆屏几何封装成了 Round 类（common/RoundScreen.ets）：

export class Round {
  static screenW: number = 466;
  static screenH: number = 466;

  /** 内切圆半径 */
  static get radius(): number {
    return Math.min(Round.screenW, Round.screenH) / 2;
  }

  /** 安全半径：内容不越界系数 0.88 */
  static get safeRadius(): number {
    return Round.radius * 0.88;
  }

  /**
   * 计算某一纵向偏移处的可用内容宽度
   * 越靠近顶部/底部，可用宽度越窄 —— 这是圆形屏排版的核心
   */
  static widthAtY(yOffset: number): number {
    const r: number = Round.safeRadius;
    const d: number = Math.min(Math.abs(yOffset), r);
    return Math.sqrt(Math.max(0, r * r - d * d)) * 2;
  }

  /** 安全圆内接正方形边长 */
  static get contentW(): number {
    return Round.safeRadius * Math.SQRT2;
  }
}

关键数字：466px 屏幕，安全半径 ≈ 205px， 内容可用高度实测只有约 330px（上下各损失约 68px）。

这就是为什么"界面显示不全"—— 把手机那套 height('100%') 布局直接搬到手表上，上下两端必定被裁。

圆屏布局三条铁律

  1. 别用 height('100%') + 居中，改为限制高度百分比（如 '92%'）+ 适度 padding
  2. 关键元素（按钮、输入框）必须落在安全圆内，装饰元素可以出血
  3. 逐行算宽度：靠近顶部/底部的行要用更窄的宽度

3.2 字号体系

手表字号必须比手机小，且要支持调节：

export enum FontScale { SMALL = 0, STANDARD = 1, LARGE = 2 }

export class Typo {
  static scale: FontScale = FontScale.STANDARD;

  static get k(): number {
    switch (Typo.scale) {
      case FontScale.SMALL:  return 0.85;
      case FontScale.LARGE:  return 1.2;
      default:               return 1.0;
    }
  }

  static get body(): number    { return 14 * Typo.k; }   // 正文
  static get caption(): number { return 11 * Typo.k; }   // 次级信息
  static get title(): number   { return 17 * Typo.k; }   // 标题
  static get display(): number { return 21 * Typo.k; }   // 大标题
}

3.3 旋转表冠（Digital Crown）

表冠是手表独有的交互硬件。Scroll / List / Slider 默认已支持表冠滚动，只有自定义交互才需要显式接管。

// API 18+，仅 Wearable 支持
Stack() {
  // ... 内容
}
.focusable(true)          // ★ 必须：组件要能获焦
.defaultFocus(true)
.focusOnTouch(true)
.onDigitalCrown((event: CrownEvent) => {
  // 输入法弹出时，表冠要让给输入法（用于移动光标）
  if (this.keyboardOn) { return; }
  this.handleCrown(event.degree);
})

本项目用 Crown.normalize() 把原始角度归一化成"步数"：

static normalize(degree: number): number {
  // 每次事件累积，每 18° 算一步
  // 反向旋转先抵消残留，避免"回拧一点却继续朝原方向走"的粘滞感
  // 单次最多 3 步，避免快速旋转跳变
}

本项目约定：

  • 登录页：转表冠 = 调节字号
  • 对话页：转表冠 = 翻动消息上下文

3.4 官方输入法接入 ★ 本次最大坑

背景

最初登录页用的是自绘键盘（自己在界面上画字母数字格子）。问题：

  1. 只有字母和数字，没有中文
  2. 圆屏上挤成一团，显示不全
  3. 用户根本没法正常登录

用户要求：全部改用手表官方输入法。

正确做法

用真正的 TextInput 组件，系统会自动拉起输入法：

@State keyboardOn: boolean = false;
private accountInput: TextInputController = new TextInputController();
private passwordInput: TextInputController = new TextInputController();

TextInput({ text: this.account, placeholder: '手机号 / 邮箱', controller: this.accountInput })
  .type(InputType.Normal)
  .id('accountField')                    // focusControl 需要 id
  .enterKeyType(EnterKeyType.Next)
  .fontSize(Typo.body)
  .height(42)
  .width('84%')
  .onFocus(() => { this.keyboardOn = true; })
  .onBlur(() => { this.keyboardOn = false; })
  .onChange((v: string) => { this.account = v; })
  .onSubmit(() => { focusControl.requestFocus('passwordField'); })

密码框：

TextInput({ text: this.password, placeholder: '请输入密码', controller: this.passwordInput })
  .type(InputType.Password)              // 系统按密码模式处理，自动掩码
  .id('passwordField')
  .enterKeyType(EnterKeyType.Done)
  .showPasswordIcon(false)               // 手表屏幕小，不显示眼睛图标
  .onSubmit(() => { this.doLogin(); })

三个 API 坑（编译报错级别）

坑 错误写法 正确写法
controller 位置 .controller(this.ctl) ❌ TextInput({ controller: this.ctl }) ✅
请求焦点 ctl.requestFocus() ❌ focusControl.requestFocus('id') + .id('id') ✅
字段跳转 手动管理状态 ❌ enterKeyType + onSubmit ✅
TextInputController 只有 3 个方法： caretPosition() / setTextSelection() / stopEditing() 它没有 requestFocus()。

★ 最硬的一条约束：官方输入法是「全屏模式」

实测发现（这是文档里不会写的）：

  1. 输入法弹出后完全覆盖 466×466 整个屏幕，应用界面在其下方完全不可见
  2. 无法在其上叠加任何悬浮按钮（画了也看不见）
  3. 该输入法底部没有回车/发送键 —— 只有：键盘切换、语音、空格、退格

这意味着：enterKeyType(Done) 和 onSubmit() 在手表上 按键不可达，不能作为唯一的提交入口。

正确的交互路径（必须这样设计）：

点输入框 → 输入法全屏弹出 → 输入内容
   → 点【右上角蓝色圆形按钮】收起键盘
   → 回到表单 → 点「登录」按钮

设计硬约束：「登录」按钮必须在收起键盘后的安全圆内可见可点。

配合 keyboardOn 状态动态压缩布局：

// 输入态：压缩品牌区，表单上移
.height(this.keyboardOn ? '52%' : '92%')
.padding({ top: this.keyboardOn ? 2 : 8, bottom: this.keyboardOn ? 0 : 8 })
// 登录时先收起输入法，避免遮挡
private async doLogin(): Promise<void> {
  this.keyboardOn = false;
  this.accountInput.stopEditing();
  this.passwordInput.stopEditing();
  // ... 执行登录
}

3.5 触控与省电

  • 最小触控区：官方建议 ≥ 96px × 96px（本项目输入框 42px 高是权衡结果，圆屏太小）
  • 省电设计：HTTP 单例连接复用、请求完成即释放、SSE 流式分片让出主线程

第 4 章 · 手机端开发（对照与扩展）

本项目当前是纯手表应用（deviceTypes: ["wearable"]）。 这一章讲如果要把同一套业务逻辑做到手机端，要改什么， 以及两端的核心差异。

4.1 两端差异总览

维度 手表端 (wearable) 手机端 (phone)
屏幕 466×466 圆形，可用高约 330px 矩形，通常 1080×2400+
布局核心 圆方程算宽、安全圆 常规响应式、断点
输入法 全屏模式，无回车键 半屏/浮起，有回车/发送键
输入提交 只能靠"收键盘 → 点按钮" 输入法回车键即可提交
独有硬件 旋转表冠 无（有侧边指纹/音量键）
字号 11–21fp（要小） 14–24fp+
触控区 紧张，需权衡 充裕，标准 48dp
网络 Wi-Fi/蓝牙共享，弱 Wi-Fi/蜂窝，强
电量敏感度 极高 中等
典型场景 抬腕即用、几秒完成 长时间沉浸使用

4.2 关键差异详解

（1）输入法：这是两端体验分化的最大点

手机端：输入法只占下半屏，应用界面上半部仍然可见， 且输入法有回车/发送键，所以可以这样：

TextInput({ text: this.inputText, placeholder: '发消息…' })
  .enterKeyType(EnterKeyType.Send)
  .onSubmit(() => { this.sendMessage(); })   // 手机端：回车即发送，体验流畅

手表端：同样这段代码，因为输入法全屏且无回车键， onSubmit 永远不会被触发。所以必须保留可见的发送按钮， 并引导用户"先收键盘再点按钮"。

💡 同一份代码，两端行为不同 —— 这是最容易被忽略的坑。 不要想当然认为 onSubmit 在所有设备上都可用。

（2）屏幕适配策略

手表端用圆方程；手机端用断点/栅格：

// 判断形态
import { display } from '@kit.ArkUI';

// 或用资源限定词：
//   resources/base/     → 默认
//   resources/wearable/ → 手表专用
//   resources/phone/    → 手机专用

鸿蒙推荐用资源限定词目录做差异化，代码里少写 if-else。

（3）表冠 vs 触摸滚动

手机端没有表冠，onDigitalCrown 不会触发。 滚动要靠 Scroll / List 的触摸手势（这些组件本身就支持）。

4.3 把本项目扩展到手机端：改动清单

如果要让 DeepSeekWatch 同时支持手机，具体要改：

① 声明设备类型

// entry/src/main/module.json5
"deviceTypes": ["wearable", "phone"]     // 加 phone

② 抽离"形态适配层"

// common/FormFactor.ets
export enum Form { WATCH, PHONE }

export class FormFactor {
  static get current(): Form {
    // 根据屏幕宽高比/圆屏特征判断
    return Round.isRound ? Form.WATCH : Form.PHONE;
  }
  static get isWatch(): boolean { return FormFactor.current === Form.WATCH; }
}

③ 页面布局分叉

build() {
  Column() {
    if (FormFactor.isWatch) {
      this.WatchLayout()      // 圆屏：限制高度、安全圆内排布
    } else {
      this.PhoneLayout()      // 手机：常规全屏布局
    }
  }
}

④ 输入提交兜底

// 手机端靠 onSend（回车），手表端必须保留可见按钮
.onSubmit(() => { this.sendMessage(); })

// 手表端额外渲染发送按钮
if (FormFactor.isWatch) {
  Button('发送').onClick(() => this.sendMessage())
}

⑤ 资源分目录

resources/
├── base/        # 通用
├── wearable/    # 手表：小图标、紧凑间距
└── phone/       # 手机：常规尺寸

⑥ 权限与能力差异

手机端可能需要额外权限（如通知、后台运行），手表端要克制。

4.4 什么时候该做"两端统一"

场景 建议
业务逻辑、网络层、数据模型 ✅ 完全复用（本项目 model/ 目录可直接复用）
页面布局、交互 ⚠️ 分叉，用条件渲染或独立布局函数
样式、尺寸 ⚠️ 用资源限定词目录
平台特有交互（表冠） ❌ 隔离在各自分支里
结论：业务逻辑下沉，UI 层分叉。 本项目的 model/（Http、AuthService、ChatService、SseClient） 已经做到了与 UI 解耦，是可以直接复用到手机端的。

第 5 章 · 签名：华为设备的生死线

5.1 首要判断：华为设备 vs OpenHarmony

选错路线会浪费大量时间：

目标设备 正确做法 自签名能否安装
华为手表/手机（HarmonyOS） 必须走 DevEco 官方自动签名 ❌ 装不上
OpenHarmony 开发板 hap-sign-tool 自签名 ✅ 可以
实测：用 OpenHarmony 社区证书自签的 HAP， 即使 verify-app 校验通过，也无法安装到华为设备。 华为只信任华为 AGC 签发的证书。

5.2 官方自动签名全流程

唯一硬前提：设备必须在线（Profile 需要内嵌设备白名单）。

DevEco Studio
  → File / 文件 → 项目结构 (Project Structure)
  → Signing Configs（签名配置）
  → 勾选 "Automatically generate signature"（自动生成签名）
  → 登录华为开发者账号
  → Apply / OK

如果设备没连上，会报：

缺少设备导致无法新建profile文件，请先通过IP或USB连接设备。

设备一连上，这个错误会自动消失，AGC 立即签发。

生成物落在：

C:\Users\<用户名>\.ohos\config\
  default_<工程名>_<hash>=.cer    # 证书
  default_<工程名>_<hash>=.p12    # 密钥库
  default_<工程名>_<hash>=.p7b    # Profile

keyAlias 固定为 debugKey。

6.1 开启无线调试

手表上：设置 → 系统和更新 → 开发人员选项 → 无线调试 → 开启 记下显示的 IP:端口（如 :45165）

hdc tconn :45165
# → Connect OK

hdc list targets -v
# → :45165   TCP   Connected   localhost   hdc

6.2 ★ 端口反查法：手表 IP 变了怎么办

核心洞察：

  • 调试端口固定（如 45165）—— 每次开启无线调试基本不变
  • IP 随 Wi-Fi 变化 —— 换网络、重新分配 DHCP 后就变了

所以：扫子网里哪个 IP 开放了 45165 端口，那就是手表。

# portscan.py
import socket, concurrent.futures

PORT = 45165
BASE = "."

def check(ip):
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.settimeout(0.6)
    try:
        if s.connect_ex((ip, PORT)) == 0:
            return ip
    except Exception:
        pass
    finally:
        s.close()
    return None

ips = [BASE + str(i) for i in range(1, 255)]
found = []
with concurrent.futures.ThreadPoolExecutor(max_workers=120) as ex:
    for r in ex.map(check, ips):
        if r: found.append(r)

print("端口 %d 开放的主机: %s" % (PORT, found if found else "无"))

配套确认本机网段：

Get-NetIPAddress -AddressFamily IPv4 | Where-Object {$_.IPAddress -like "192.168.*"}
💡 重要教训：手表会休眠断网。 实测中多次遇到"刚才还连着，一会儿就 Offline"。 若 hdc tconn 失败，先让手表亮屏操作一下，再重试。

7.2 ★★ hdc file send 三大陷阱

这是本次调试耗时最久的坑，务必记住。

陷阱 1：目标必须是「目录」，不是文件路径

# ❌ 错误
hdc file send app.hap /data/local/tmp/app.hap
# → [Fail]Not a directory, path:/data/local/tmp/app.hap

# ✅ 正确（末尾带 /）
hdc file send app.hap /data/local/tmp/
# → 落盘为 /data/local/tmp/app.hap

陷阱 2：源文件在 Git Bash 里会被错误拼接

# ❌ 错误
hdc file send /d/HarmonyBuild/app.hap /data/local/tmp/
# → open path:d:\.workbuddy\11\/d/HarmonyBuild/app.hap, error:no such file or directory

# ✅ 正确：cd 到文件目录，用相对文件名
cd /d/HarmonyBuild && hdc file send app.hap /data/local/tmp/

陷阱 3：带连字符的文件名会被截断

# ❌ entry-default-signed.hap 传过去只剩 entry 目录
# ✅ 先 cp 成简单名字
cp entry-default-signed.hap /d/HarmonyBuild/app.hap

错误码对照

报错 原因 解法
code:9568269 install file path invalid 目标被当成目录 按三步法重传，ls -la 验证是文件
Error opening file: no such file or directory Git Bash 绝对路径被拼接 cd + 相对文件名
[Fail]Not a directory 目标写成了文件路径 目标写成 /data/local/tmp/

可靠三步部署法

export PATH="/d/DevEco Studio/sdk/default/openharmony/toolchains:$PATH"

# 1. 换简单文件名
cd /d/HarmonyBuild/DeepSeekWatch/entry/build/default/outputs/default
cp entry-default-signed.hap /d/HarmonyBuild/app.hap

# 2. 相对路径 + 目录目标
cd /d/HarmonyBuild
hdc file send app.hap /data/local/tmp/

# 3. ★ 必须验证字节数一致，再安装
hdc shell "ls -la /data/local/tmp/app.hap"
hdc shell "aa force-stop com.dswatch.round"
hdc shell bm install -p /data/local/tmp/app.hap
hdc shell aa start -a EntryAbility -b com.dswatch.round -m entry

第 9 章 · 实战复盘：六个真实 Bug（+ 真机验证方法）

9.1 Bug 1：登录报"未能获取登录凭证"

现象：账号密码正确，点登录却报"未能获取登录凭证"。

定位过程：不猜，直接抓真实响应。

import json, base64, os, urllib.request
payload = {
    'email': '', 'mobile': '<手机号>', 'password': '<密码>',
    'area_code': '+86', 'device_id': did, 'os': 'web'
}
req = urllib.request.Request(
    'https:///api/v0/users/login',
    data=json.dumps(payload).encode(),
    headers={'Content-Type': 'application/json'},
    method='POST')
print(json.loads(urllib.request.urlopen(req).read().decode()))

真实响应：

{
  "code": 0,
  "data": {
    "biz_code": 0,
    "biz_data": {
      "user": {
        "id": "a86ee518-...",
        "token": "pz2fNBdjtB4pE8m8...",      ← token 在这里！
        "mobile_number": "191******48",
        "id_profile": { "name": "夜白" }      ← 昵称在这里！
      }

根因：

字段 ❌ 代码读的 ✅ 真实位置
token biz_data.token biz_data.user.token
昵称 user.name（恒空） user.id_profile.name

修复：

// 新增兼容方法
private static pickToken(o: Record<string, Object>): string {
  const tk: Object | undefined = o['token'];
  if (tk === undefined || tk === null) return '';
  if (typeof tk === 'string') return tk as string;
  const to: Record<string, Object> = tk as Record<string, Object>;
  const v: Object | undefined = to['value'];
  return (typeof v === 'string') ? v as string : '';
}

// 三级兜底
let token: string = '';
const uObj: Object | undefined = bd['user'];
if (uObj !== undefined && uObj !== null) {
  token = AuthService.pickToken(uObj as Record<string, Object>);   // 1) user.token
}
if (token.length === 0) {
  token = AuthService.pickToken(bd);                                // 2) 顶层兜底
}

方法论：

遇到"接口返回了但解析不到"，不要读代码猜， 用脚本打一次真实接口，把响应 dump 出来看。快 10 倍。

9.3 Bug 3：点"发消息"框完全没反应

现象：对话页点输入框，什么都不发生。

根因：代码里 @State editing 被赋值（this.editing = true）， 但全篇从未被读取过 —— 是个死变量。所谓的"输入框" 其实只是一个长得像输入框的 Row()，根本不能输入。

修复：替换为真正的 TextInput：

TextInput({ text: this.inputText, placeholder: '发消息…', controller: this.inputCtl })
  .type(InputType.Normal)
  .enterKeyType(EnterKeyType.Send)
  .layoutWeight(1)
  .onFocus(() => { this.keyboardOn = true; })
  .onBlur(() => { this.keyboardOn = false; })
  .onChange((v: string) => { this.inputText = v; })
  .onSubmit(() => { this.sendMessage(); })

并在发送时收起输入法：

this.inputCtl.stopEditing();
this.keyboardOn = false;

9.4 Bug 4：消息本地显示了，但服务端根本没收到

现象：手表上发消息，气泡正常出现、转圈、然后显示回复（或报错）， 但用同一账号在手机/网页端看，完全没有这条对话记录。

根因：服务端返回 {"code":40301,"msg":"INVALID_POW_RESPONSE"}。 PoW（工作量证明）没通过，请求在网关层就被拒了 —— 消息从未进入 DeepSeek。

PoW 实现有三处错误：

项 错误实现 正确实现
哈希 标准 SHA3-256 DeepSeekHashV1 = Keccak-f[1600] 跳过 round 0（只做 rounds 1..23）
前缀 salt + "_" salt + "_" + expire_at + "_"
判定 摘要前 3 字节 ≤ difficulty hash == challenge（32 字节精确相等）；difficulty 是 nonce 搜索范围上界 [0, difficulty)

怎么定位的：写一个 Python 脚本完整复现「登录 → 取挑战 → 求解 → 发送 → 回查历史」， 一眼看到 chat_messages: []。再对照社区 Go 参考实现逐行比对，三处差异一目了然。

方法论：界面上"看起来成功"不等于"服务端收到了"。 凡是"发出去没效果"的问题，先用脚本独立复现一遍请求链路， 别在 UI 层猜。

哈希实现要点（手表性能是硬约束）：

// ❌ 用 BigInt 实现：单次哈希约 0.2ms，144000 次尝试要 30 秒以上，手表上不可用
// ✅ 把 64 位 lane 拆成两个 32 位整数（hi / lo）
BH[10] = (H[1] << 1) | (L[1] >>> 31);   // rotl64(lane, 1)
BL[10] = (L[1] << 1) | (H[1] >>> 31);

再叠加两个优化：

  1. ρ/π 手工展开成 25 条语句，避免内层取模和分支；
  2. 求解时复用前缀状态 —— salt_expireAt_ 是固定的，

nonce 最多 7 位，每次只有 2 个 lane 需要重算。

两个隐蔽的坑：

// 坑 1：challenge 是 64 字符 hex，每 2 字符 = 1 字节（大端书写）
//       lane 的低 32 位 = bytes[0..3] 的「小端」组合
// ❌ parseInt(hex.substring(0, 8), 16)  → 字节序正好反了，求解必然失败
const tb: number[] = [];
for (let i = 0; i < 32; i++) {
  tb.push(parseInt(challengeHex.substring(i * 2, i * 2 + 2), 16));
}
const t0l = (tb[0] | (tb[1] << 8) | (tb[2] << 16) | (tb[3] << 24)) >>> 0;

// 坑 2：单块吸收时状态初值为 0，受 nonce 影响的 lane 要「直接赋值」
//       完整 lane 值，不是和模板 lane 做异或（会重复计入前缀字节）
H[ln] = hi;   // ✅
L[ln] = lo;

验证技巧：把 .ets 粗转成 .mjs 在 Node 里跑算法回归 —— ArkTS 与 JS 的 32 位运算语义完全一致，比反复编译 HAP 快十几倍。 本项目里的 ets2js.py + test/run.mjs 就是干这个的， 用 3 组真实 challenge/answer 做回归，全绿再编译。

9.5 Bug 5：PoW 过了，界面还是一片空白（SSE 格式对不上）

现象：修好 PoW 后消息能进服务端了，但手表上助手气泡始终是空的。

根因：SSE 解析写错了格式假设。代码只认：

event: delta
data: {"type":"RESPONSE","content":"你"}

而真实流里只有 ready / update_session 带 event，正文帧一律不带， 是 JSON-Patch 风格：

event: ready
data: {"request_message_id":1,"response_message_id":2,"model_type":"default"}

data: {"v":{"response":{"message_id":2,...,"status":"WIP"}}}
data: {"p":"response/content","o":"APPEND","v":"你好"}
data: {"v":"！"}          ← 省略 p/o，沿用上一帧的 path 与 op

原实现对「没有 event 名的帧」直接 return，正文被 100% 丢弃。

修复要点：

  1. 无 event 名的帧当作 patch 帧处理，按 p / o / v 解析；
  2. v 是字符串且没带 p → 延续帧，沿用上一帧的 path / op；
  3. 只有 *.content 路径才更新 lastPath/lastOp ——

否则 response/accumulated_token_usage 这类统计帧会污染状态， 后面紧跟的延续帧被丢掉，正文莫名断流；

  1. {"code":40301,"msg":"..."} 也是无 event 的裸帧，要转成错误提示，

否则又是"静默失败"；

  1. decode() 统一 \r\n → \n：分帧只按 \n\n 切，不归一化会一帧都切不出。
教训：这两个 Bug 的共同点是「静默失败」—— 界面没有任何异常，只是"没效果"。 所以错误信息一定要显式暴露出来（本项目把服务端 code 映射成中文提示）， 否则排查成本会高一个数量级。

9.6 真机上怎么验证"改对了"（没有单步调试时）

手表上没有断点调试器，也不方便看界面（屏幕只有 466×466）。 本项目用的是「启动自检 + hilog」这套组合，实测非常高效。

核心思路：把算法自检放到 Ability 启动里

// EntryAbility.ets
const TAG: string = 'Boot';

onCreate(): void {
  Store.init(this.context);
  // ★ 启动自检：DeepSeekHashV1 移植是否正确，直接决定 PoW 能否过
  const ok: boolean = DeepSeekHash.selfTest();
  console.info(TAG + ' selfTest=' + (ok ? 'PASS' : 'FAIL'));
}

这样每次冷启动都会主动汇报一次，不用等着用户操作触发。

9.7 Bug 6：点"发送"后 App 直接消失（THREAD_BLOCK_6S）

现象

前面的 Bug 全修完、真机上也能看到 pow start 日志了， 但一点发送，App 就没了 —— 不是崩溃弹窗，是界面直接回表盘。

定位

hdc shell "hilog -x | grep -iE 'ThreadBlock|AppKilled|faultloggerd'"
C01311/foundation/AppMS: [AMSI7783]name: THREAD_BLOCK_6S, faultType: 3,
    uid: 20020129, pid: 49178, bundleName: com.dswatch.round,
    faultData.forceExit:1
C02DA0/hiview/AppKilledReporter: Report: ... reason: ThreadBlock6S,
    isForeground: 1, bundleName: com.dswatch.round

THREAD_BLOCK_6S + forceExit:1 —— 系统检测到主线程 6 秒没响应事件， 直接强杀进程。这是穿戴设备上很常见的死法。

根因

PoW 要算几万次 Keccak（difficulty 实测 144000）。 原实现已经很"小心"了：

const SLICE: number = 1500;
for (let n = 0; n < difficulty; n++) {
  // ...算哈希...
  tried++;
  if (tried % SLICE === 0) {
    await DeepSeekHash.yield_();       // setTimeout(0) 让出主线程
  }
}

但在手表上这依然不够： await setTimeout(0) 的"让出"只是把后续代码排进宏任务队列， 是否真的被调度、什么时候被调度，取决于主线程是否空闲。 主线程持续有 UI 工作（帧刷新、动画、输入法）时， 这些回调会被不断推迟，累积起来就超过了 6 秒的判定窗口。

一句话：在手表上，任何超过 1~2 秒的密集计算都不能放主线程， 靠 await setTimeout(0) 切片是不可靠的。

解法：taskpool 把计算挪到后台线程

HarmonyOS 提供了两个方案，这里选 taskpool：

方案 成本 适用
Worker 要单独建 .ets 文件 + 手写消息协议 + 管生命周期 长期运行的后台任务
taskpool 只需一个 @Concurrent 函数，系统调度线程池 一次性密集计算（本项目正是）

第一步：把核心循环抽成纯同步函数（不 await、不 yield）

// DeepSeekHash.ets
/**
 * 在 [from, to) 区间内同步搜索 nonce，命中返回 nonce，否则 -1
 * ⚠️ 纯计算 —— 必须跑在后台线程
 */
static searchRange(prefix: string, challengeHex: string,
  from: number, to: number): number {
  for (let n = from; n < to; n++) {
    // ...写 nonce + permute...
    if (匹配 challenge) { return n; }
  }
  return -1;
}

第二步：用 @Concurrent 包装成可投递的任务

// PowTask.ets
import taskpool from '@ohos.taskpool';
import { DeepSeekHash } from '../common/DeepSeekHash';

@Concurrent
function powRange(prefix: string, challengeHex: string,
  from: number, to: number): number {
  return DeepSeekHash.searchRange(prefix, challengeHex, from, to);
}

第三步：分段投递 —— 主线程只 await，不参与计算

export async function solvePowAsync(prefix: string, challengeHex: string,
  difficulty: number, budgetMs: number,
  onProgress?: (tried: number, total: number) => void): Promise<number> {
  const SEG: number = 8000;
  for (let from = 0; from < difficulty; from += SEG) {
    const to = Math.min(difficulty, from + SEG);
    const task = new taskpool.Task(powRange, prefix, challengeHex, from, to);
    const hit = await taskpool.execute(task) as number;   // 真正异步等待
    if (hit >= 0) { return hit; }
    if (onProgress) { onProgress(to, difficulty); }        // 每段回来更新进度
    if (Date.now() - start > budgetMs) { return -1; }
  }
  return -1;
}

为什么分段而不是一次性丢进去？

一次丢 difficulty 进去虽然也能算，但：

  1. taskpool 内部无法回调 UI —— 不分段的話进度条动不了，用户以为卡死
  2. 命中即停能省掉大量无用计算（实测命中位置常在 1/3 处）
  3. 超时预算（budgetMs）也只能在段间检查

@Concurrent 的硬约束（官方文档 + 实测）

约束 说明
❌ 不能捕获闭包变量 所有输入必须显式作为参数传递（所以上面四个参数全传）
❌ 不能调用当前文件内定义的其他函数 同文件函数属于"闭包变量"，会报<br>Only imported variables and local variables can be used in @Concurrent decorated functions
✅ 可以调用 import 进来的函数 / 类的静态方法 所以 PowTask.ets 必须单独成文件再 import DeepSeekHash，<br>不能直接把 powRange 塞进 DeepSeekHash.ets
❌ 不能是 async / 返回 pending Promise 会报 Can't return Promise in pending state
❌ 不能标注 generator / 箭头函数 / 类方法 只能是具名函数声明或 async 具名函数
❌ 不能用 UI / AppStorage 等非线程安全模块 工作线程只能用线程安全模块（hilog、taskpool 可以）
⚠️ CPU 执行时长上限 3 分钟（LongTask 除外） 纯计算要分段，别一次性丢几万次哈希进去
为什么 PowTask.ets 要单独建文件 —— 这条最容易踩。 直觉上会把 powRange 直接写在 DeepSeekHash.ets 里（反正逻辑在一起）， 但它要调用同文件的 permute，就违反了上表第二条，编译期直接报错。 拆成两个文件、import 进来就合法了。

验证后台线程里的代码是否"干净"：
