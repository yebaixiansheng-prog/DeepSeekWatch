> 实测时间：2026-09-19。数据来源：`<API_HOST>` 线上 bundle `main.7d19d7e901.js` + 微信 `wxLogin.js` + 真实接口调用。

## 0. 一页结论（TL;DR）

| 问题 | 结论 |
|---|---|
| DeepSeek 有微信扫码登录吗 | **有**。web 端「使用微信扫码登录」，走微信开放平台 `snsapi_login` |
| 二维码怎么来的 | 微信官方 `WxLogin` 组件在页面里**内嵌一个 `open.weixin.qq.com` 的 iframe**，二维码由微信服务器渲染在 iframe 内 |
| 扫码后怎么拿 token | 微信回调 `https://<API_HOST>/oauth/wechat/callback?code=...`，该页再 **`POST /oauth/get_token`** `{nonce, provider}` 换 DeepSeek token |
| 手表能直接显示这个二维码吗 | ❌ **不能直接用现成接口**。`qrconnect` 页面拒绝非浏览器来源（实测返回 `qqBS_a089916-0` 错误页），且二维码是**在微信域内渲染的 iframe**，ArkTS 拿不到图片 URL |
| 那手表怎么办 | ✅ 已落地 **路线 B：手表显示「配对码」→ 手机网页扫码 → 手表轮询取 token**（见第 5、6 节）。代码已完成并编译通过；**中继服务端尚未部署**（`RELAY_BASE` 为空占位符，此时 UI 会明确提示「尚未开放」而不是假装能用，见 §8.2） |
| 与密码登录兼容性 | ✅ 完全兼容：**共用 `AuthService` 登录态落盘出口 + 共用 `LoginPage.finishLogin()` 跳转**，UI 层只多一个入口，两者产出的 token 完全等价 |

## 1. 背景与目标

### 1.1 为什么要在手表上做微信扫码登录

手表端当前**只有密码登录**（设计取舍见 `AuthService` 注释与 `API_SPEC` §2）。密码登录在手表上有两个真实痛点：

1. **输入成本极高**：466px 圆屏 + 官方输入法占掉近半屏，输一次「邮箱 + 高强度密码」对用户是折磨；
2. **风控敏感**：密码登录需要一次性提交账号密码，出口 IP 不可信时直接吃 `RISK_DEVICE_DETECTED`（biz_code=11，见 Bug 15）。

微信扫码登录能同时缓解这两点：**用户不碰键盘**；且扫码链路复用微信的既有登录态，设备可信度更接近「真实用户」。

### 1.2 目标

- 在 `LoginPage` 增加「微信扫码登录」入口，与密码登录**并存、可切换**；
- 明确二维码的获取、展示、状态回调、登录态建立四段流程；
- 给出**降低风控识别风险**的具体措施；
- 明确**手表端的硬约束边界**，不做无法落地的承诺。

## 2. ★ 实测逆向：DeepSeek 微信登录的真实契约

> 以下全部来自对线上 bundle 的直接逆向，**不是推测**。所有路径、字段名、错误码均可在 `main.7d19d7e901.js` 中搜到。

### 2.1 全流程时序

```
┌──────────┐      ① 点「使用微信扫码登录」      ┌────────────────────┐
│  客户端   │ ───────────────────────────────▶ │  DeepSeek web 端    │
│ (含手表)  │                                  │  (<API_HOST>)│
└──────────┘                                  └─────────┬──────────┘
                                                        │ ② GET /api/v0/client/wechat_js_sdk_signature?url=...
                                                        │    → { appid, timestamp, noncestr, signature }
                                                        ▼
                                              ┌──────────────────────┐
                                              │ 微信开放平台           │
                                              │ WxLogin 渲染 iframe：  │
                                              │ open.weixin.qq.com/   │
                                              │ connect/qrconnect     │
                                              │   ?appid=             │
                                              │   &scope=snsapi_login │
                                              │   &redirect_uri=      │
                                              │     .../oauth/wechat/ │
                                              │        callback       │
                                              └──────────┬───────────┘
                                                         │ ③ 用户用微信 App 扫码并确认
                                                         ▼
                        ④ 微信带 code 重定向到 redirect_uri
                 https://<API_HOST>/oauth/wechat/callback
                        ?code=<WECHAT_CODE>&state=...
                                                        │
                                                        ▼
                  ⑤ 回调页 POST /oauth/get_token  { nonce, provider:"WECHAT" }
                     → biz_data.token  ★ 这就是 DeepSeek 的 userToken
```

### 2.2 关键接口清单（实测）

| # | 接口 | 方法 | 用途 | 备注 |
|---|---|---|---|---|
| 1 | `/api/v0/client/wechat_js_sdk_signature` | GET | 取微信 JSSDK 签名 | **query 传 `url`**；返回 `appid/timestamp/noncestr/signature` |
| 2 | `open.weixin.qq.com/connect/qrconnect` | GET | 二维码页（iframe src） | 参数见 2.3；**非浏览器来源会被拒** |
| 3 | `/oauth/wechat/callback` | GET | 微信回调用（redirect_uri） | 带 `code` / `state` |
| 4 | **`/oauth/get_token`** | **POST** | **用 nonce 换 DeepSeek token** | body `{nonce, provider}`；`provider ∈ {"GOOGLE","APPLE","WECHAT"}` |
| 5 | `/oauth/wechat/bind` | — | 已有账号绑微信 | 账号体系用，非登录必需 |
| 6 | `/oauth/wechat/unbind` | — | 解绑 | 同上 |
| 7 | `/oauth/wechat/mobile_verification` | — | 微信登录后若需补绑手机 | **新增用户可能触发** |

### 2.3 `qrconnect` 参数（来自微信官方 `wxLogin.js` 源码）

微信官方组件（`https://res.wx.qq.com/connect/zh_CN/htmledition/js/wxLogin.js`，仅 1563 字节）本质就做一件事：**拼 URL + 塞 iframe**。其拼接逻辑：

```js
"https://open.weixin.qq.com/connect/qrconnect?appid=" + o.appid
+ "&scope="          + o.scope                 // snsapi_login
+ "&redirect_uri="   + o.redirect_uri          // 必须 URL 编码
+ "&state="          + o.state
+ "&login_type=jssdk"                          // ★ 走 iframe 模式的关键
+ "&self_redirect="  + n                       // true/false/default
+ "&styletype=" + ... + "&sizetype=" + ... + "&bgcolor=" + ... + "&rst=" + ...
+ "&ts="             + Date.now()              // 防缓存
+ (stylelite===1 ? "&stylelite=1" : "")
+ (fast_login===0 ? "&fast_login=0" : "")      // ★ 默认 fast_login=1
+ "&color_scheme="   + o.color_scheme;         // light / dark / auto
```

> **实测的 appid（公开值，客户端可见）**：`wx9fdce37c3d31a2de`
> 取自 `/api/v0/client/wechat_js_sdk_signature` 的真实响应。

DeepSeek 实际调用（反混淆后）：

```js
new window.WxLogin({
  self_redirect: i, id: n, appid: a,
  scope: "snsapi_login",
  redirect_uri: t,
  stylelite: 1,
  color_scheme: l,          // light / dark / auto
  state: o ? "beta" : "",
  fast_login: 1,
  onQRcodeReady: () => { /* 上报"微信登录组件渲染成功" */ }
})
```

### 2.4 ★ token 交换（最关键的一步）

回调页逻辑（bundle 内 `function eX(e)`，反混淆）：

```js
let e = h.get("nonce");          // ← 从 URL query 取
let s = h.get("provider");       // ← "WECHAT" / "GOOGLE" / "APPLE"
if (e && ["GOOGLE","APPLE","WECHAT"].includes(s)) {
  const { data: { token: n } } = await getToken({ nonce: e, provider: s });
  setPersistedCurrentUser(n, null);      // ★ token 落盘
  const { data: { user: r } } = await getCurrentUser();   // 再取用户信息
  beAuthenticated(r);
  // 埋点：signInWithWechatOK / signInWithWechatFailed
}
```

对应的请求实现：

```js
function F(e, t) {   // e = {nonce, provider}
  return http.post(baseUrl + "/oauth/get_token", {
    json: { nonce: e.nonce, provider: e.provider }
  }).then(res => {
    const r = res.json.data;
    if (!r.biz_data?.token) {
      throw Error(`Unable to get token, code: ${r.biz_code}, msg: ${r.biz_msg}`);
    }
    return { data: { token: r.biz_data.token } };
  });
}
```

**要点**：
- 这是**普通 JSON POST**（不是 SSE），响应形如 `{code, data:{biz_code, biz_data:{token}}}`；
- 拿到 token 后**还要调 `/api/v0/users/current`** 取用户资料（与密码登录不同，get_token 只给 token）；
- `nonce` 由服务端在回调跳转时带上，**客户端无法自行构造**。

## 3. ★ 硬约束：为什么不能直接把手表变成「浏览器」

这是本设计**最重要的一节**。不做这一步验证就会写出一个跑不通的方案。

### 3.1 实测证据

直接以普通 HTTP 客户端请求微信二维码页：

```bash
curl "https://open.weixin.qq.com/connect/qrconnect\
?appid=wx9fdce37c3d31a2de&scope=snsapi_login\
&redirect_uri=https%3A%2F%2F<API_HOST>%2Foauth%2Fwechat%2Fcallback\
&login_type=jssdk" \
  -H "Referer: https://<API_HOST>/sign_in" \
  -H "User-Agent: Mozilla/5.0 ... Chrome/126.0.0.0 ..."
```

结果：**HTTP 200，但返回 892 字节的错误页**，正文含错误码 `qqBS_a089916-0`。
加 `Referer`、补全 `login_type=jssdk`/`ts`、模拟完整 UA —— **全部无效，恒为 892 字节错误页**。

### 3.2 三条拒绝原因（叠加）

| # | 原因 | 说明 |
|---|---|---|
| 1 | **域名绑定的来源校验** | `qrconnect` 只对**在微信开放平台登记过、且请求来自该域真实页面**的来源出码。裸 HTTP 客户端拿不到 `Referer` 与同源上下文，被判为伪造 |
| 2 | **二维码不在 HTTP 响应里** | 二维码是 `WxLogin` 塞进页面的 **iframe 内部由微信服务器渲染**的。`qrconnect` 返回的是**壳页面**，即使拿成功也**只是一个 HTML，没有图片 URL 可下载** |
| 3 | **交互依赖 `postMessage`** | 扫码状态（`wxReady` / `wxQRcodeReady`）通过 `window.addEventListener("message")` 从 `open.weixin.qq.com` 回调，且**校验 `event.origin === "https://open.weixin.qq.com"`**。纯原生客户端没有这个事件通道 |

> 旁证：微信官方组件的 `wxLogin.js` 全文只有 1563 字节，它**不含任何二维码生成逻辑** ——
> 只做「拼 URL + 创建 iframe + 监听 postMessage」。二维码完全在微信域内产生。
> **所以「自己抓图片字节」这条路从根上就是错的。**

### 3.3 手表侧的额外约束

| 约束 | 说明 |
|---|---|
| 无内置 `Web` 组件使用先例 | 工程当前**未引入** `Web` 组件（`module.json5` 只有 INTERNET / GET_NETWORK_INFO 权限），需新增 `ohos.permission.INTERNET` 之外的 webview 相关配置 |
| 穿戴端 ArkWeb 支持面窄 | `deviceTypes: ["wearable"]`。ArkWeb 在穿戴形态上的可用性/内核完整性**低于手机**，且 DeepSeek 官方也从不把 web 登录页适配到 466px 圆屏 |
| 圆屏尺寸 | 466px 物理像素、density=2 → **1vp = 2px**。微信二维码组件固定 **300×400px**（`frame.width/height` 写死），在圆屏**必然溢出被裁**，扫不出来 |
| 二维码容量 | 二维码需 ≥ 一定模块数才可扫。在圆屏可用区域内（安全圆直径约 466px，内边距后约 380px）勉强放得下，但**前提是能拿到二维码图片** —— 而这一步已被 3.2 否决 |

**结论：手表端「自己渲染微信二维码」不可行。** 不要再尝试抓 `qrconnect`。

## 4. 可行方案设计

### 4.1 路线对比

| 路线 | 做法 | 可行性 | 评价 |
|---|---|---|---|
| **A. 手表出码 + 手机扫**（推荐） | 手表调 DeepSeek 侧接口拿「登录用二维码内容」，画在表盘；用户用手机微信扫 → 手机侧完成 OAuth → 手表轮询拿到 token | ✅ 可行 | 需 DeepSeek 提供「设备码登录」类接口；若暂无可先落地 B |
| **B. 手机端代登录 + 手表取 token** | 手表展示 6~8 位**配对码**；用户在手机浏览器/App 完成微信扫码登录后，输入配对码把 token 推给手表 | ✅ 可行 | **不依赖微信 iframe**，纯自建中继；实现成本最低 |
| C. 手表内嵌 WebView 打开 DeepSeek 登录页 | 用 `<Web>` 组件加载 `<API_HOST>/sign_in`，让它自己跑 `WxLogin` | ⚠️ 理论可行、实践高风险 | 圆屏 OCR/扫码体验极差；ArkWeb 在 wearable 上是否支持 `postMessage`+iframe 未知；且与风控"非浏览器指纹"矛盾 |
| D. 直接复用 `WxLogin` iframe URL 抓图 | — | ❌ 不可行 | 已由第 3 节实测否决 |

### 4.2 推荐落地顺序

> **务实建议**：先做 **B**（纯自建中继，1~2 天可交付、零平台依赖），
> 同时向 DeepSeek 侧确认是否有官方「设备码 / 扫码登录」接口以升级到 **A**。
> 本文档第 6 节给出 B 的完整实现设计。

## 5. 兼容性设计（与现有密码登录并存）

这是用户明确要求的「保证与现有登录方式兼容」。核心思路：**登录方式只是「token 的产地」，登录态本身不需要区分来源。**

### 5.1 分层设计

```
                  ┌─────────────────────────────┐
                  │        LoginPage            │   ← 只改 UI 层
                  │  ┌───────────┬───────────┐  │
                  │  │ 密码登录   │ 微信扫码   │  │   新增 Tab/入口
                  │  └─────┬─────┴─────┬─────┘  │
                  └────────┼───────────┼────────┘
                           ▼           ▼
              AuthService.login()   AuthService.loginByQr()
                           │           │
                           └─────┬─────┘
                                 ▼
                    ★ 同一个「登录态落盘」出口
              Store.put(TOKEN) + Store.put(USER)
                    AuthService.token / user
                                 │
                                 ▼
                Index / ChatPage / HistoryPage  ← 完全无感
```

### 5.2 兼容要点

| 要点 | 做法 |
|---|---|
| **token 语义一致** | 两种方式最终都产出**同一个 `userToken`**（微信路径来自 `/oauth/get_token`），后续 Bearer 鉴权完全一致，下游零改动 |
| **落盘 key 不变** | 仍写 `Keys.TOKEN` / `Keys.USER`，`restore()` 无需感知登录来源 |
| **device_id 复用** | 微信路径**同样**必须带 `x-<prefix>-device-id` / `x-ds-platform`，复用 `ensureDeviceId()` 的持久化 id，**不要**新建一套 |
| **UI 可切换** | `LoginPage` 用 `@State loginMode: 'password' \| 'wechat'`，顶部两个分段；切换时清 `errMsg`，`keyboardOn` 归位 |
| **返回栈不变** | 微信登录成功后走**同一段** `router.clear() → replaceUrl('pages/Index')`，避免 Bug 12（栈里两个入口页）重现 |
| **退出登录一致** | `AuthService.logout()` 不变（调 `logout_all_sessions`），同时清 token/user |
| **风控文案复用** | `biz_code=11` 的用户指引文案（"先用浏览器在同一网络登录一次"）在两条路径上**共用同一份** |
| **不破坏现有回归** | `pow-verify` / `sse-parser-test` / `fingerprint-check` 三个离线回归必须保持全绿；改 `Constants` 后**必跑** `fingerprint-check.mjs` |

### 5.3 建议的接口形态（`AuthService` 新增，不修改现有 `login()`）

```ts
/** 扫码/配对登录的对外结果，与 LoginResult 同构，便于 UI 统一处理 */
static async loginByQr(sessionId: string, pollIntervalMs: number): Promise<LoginResult>
```

> 关键纪律：**不要把扫码逻辑塞进现有 `login()`**。
> 现有 `login()` 有完整的风控字段拼装与错误码映射（Bug 15 的成果），
> 混改会牵动已验证的密码路径。

## 6. 路线 B 实现设计（自建中继，无平台依赖）

### 6.1 整体流程

```
手表                          自建中继服务                    手机
 │ ① POST /device/start          │                             │
 │──────────────────────────────▶│                             │
 │ ◀── { deviceCode, userCode,   │                             │
 │       verifyUrl, expiresIn }  │                             │
 │                               │                             │
 │ ② 显示：userCode(6位)          │                             │
 │    + verifyUrl 的域名/短码      │                             │
 │                               │                             │
 │ ③ 轮询 GET /device/poll        │   ④ 手机打开 verifyUrl       │
 │    ?device_code=...           │◀────────────────────────────│
 │    (每 3~5 秒)                │   ⑤ 在网页上完成微信扫码登录   │
 │                               │      (服务端跑 OAuth，非手表)  │
 │                               │   ⑥ 中继拿到 DeepSeek token   │
 │                               │      绑定到该 deviceCode      │
 │ ◀── { status:"ok", token }    │                             │
 │ ⑦ 落盘 token → 进主页面        │                             │
```

### 6.2 状态机

| 状态 | 含义 | 手表行为 |
|---|---|---|
| `pending` | 尚未被扫描 | 继续轮询，显示「等待扫码」 |
| `scanned` | 已扫码待确认 | 显示「已扫码，请在手机上确认」 |
| `ok` | 完成，附 token | 落盘并跳转 |
| `expired` | 超过 `expiresIn` | 停止轮询，提示「二维码已过期，点击刷新」 |
| `denied` / `error` | 用户在手机侧拒绝或出错 | 停止轮询，展示原因 + 重试入口 |

**轮询纪律**（与 SSE 看门狗同源思路 —— 任何网络操作都必须有失败出口）：

- 轮询间隔 **3~5s**，带**指数退避**（网络抖动时 5→10→20s 上限），避免打爆服务端；
- 轮询总时长必须有**硬上限**（建议 = `expiresIn`，通常 300s）；
- 到上限务必**停止定时器并给明确 UI 反馈**，绝不出现「永久转圈」；
- 页面销毁（`aboutToDisappear`）必须 `clearInterval` —— 参考本项目 Bug 17 的定时器纪律。

### 6.3 手表端 UI（466px 圆屏）

```
        ┌─────────────────────┐
        │     微信扫码登录      │   ← Typo.caption
        │                     │
        │   ┌─────────────┐   │
        │   │   8 2 4 1   │   │   ← 6~8 位配对码，超大字号
        │   │   9 3 7 5   │   │      （这是手表上最有用的信息）
        │   └─────────────┘   │
        │                     │
        │  在手机浏览器打开：    │
        │  ds.example.com/pair │   ← 域名/短链，字号小一档
        │                     │
        │   ◷ 等待扫码…        │   ← 状态行，随状态变化
        └─────────────────────┘
```

**为什么是「配对码」而不是二维码？**
- 圆屏**放得下二维码内容但扫起来极难**（用户要拿手机对准手表小屏，且手表屏幕反光/曲率大）；
- 手表的核心优势是**显示大号数字**，配对码正合适；
- 二维码渲染在**手机网页**上完成 —— 那里才是 `WxLogin` 能正常工作的环境。

**布局纪律**（沿用本工程经验）：
- `1vp = 2px`，安全圆内可用宽度约 **380px ≈ 190vp**；
- 配对码用 `Typo.title + 若干` 并**固定 2 行**，避免换行把底部状态行顶出屏幕；
- 底部状态行**永不隐藏**（对应 Bug 17 的教训：不能让用户面对"什么都不知道"的界面）。

### 6.4 中继服务端（伪契约，供自建时对齐）

| 接口 | 方法 | 请求 | 响应 |
|---|---|---|---|
| `/device/start` | POST | `{client_id, device_hint}` | `{device_code, user_code, verify_url, expires_in, interval}` |
| `/device/poll` | GET | `?device_code=...` | `{status, token?, user?, error?}` |
| `/pair/verify` | POST | `{user_code, token, user}` | `{ok}` —— 手机侧登录成功后回填 |

> `device_code` 是**设备侧密钥**（长随机串，只给手表）；
> `user_code` 是**人类可读短码**（给用户看/输）。
> 两者分离是 OAuth Device Authorization Grant（RFC 8628）的标准做法，避免短码被暴力猜中直接换 token。

## 7. 降低风控识别风险

这是用户问题的第 4 问。核心认知（来自 Bug 15 的实战结论）：
**风控识别的不是「网络」，而是「这个请求像不像真实客户端」。**

### 7.1 必须继承的既有措施（两条路径共用）

| 措施 | 原因 | 现状 |
|---|---|---|
| `device_id` **长期稳定**（持久化） | 每次随机 = 风控眼里的「陌生设备」 | ✅ `ensureDeviceId()` 已做，**不要动** |
| 登录体字段齐全 | `device_name`/`device_model`/`token`/`platform`/`os` 都参与设备可信度评分 | ✅ 密码路径已补齐，**扫码路径同样要带** |
| UA 结构完整 | 旧 UA 自称 Mozilla 却无 Chrome 版本号 → 与「脚本客户端」强相关 | ✅ 已换成完整移动端 Chrome UA |
| 全请求带 `x-<prefix>-device-id` / `x-ds-platform` | 缺失会被当成未知客户端 | ✅ `Http.buildHeaders()` 统一加 |
| 冷启动预热 `DeviceIdCache` | 否则首个请求不带设备头 | ✅ `AuthService.warmUp()` |

### 7.2 扫码登录新增的风险点与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **轮询过频** | `/device/poll` 高频请求会被当成爬虫 | 间隔 ≥3s + 指数退避 + 尊重服务端 `interval` |
| **中继服务成为新指纹** | 自建服务的域名/证书与 DeepSeek 无关，中继侧请求要**如实、完整**地转发设备字段 | 中继转发时**完整透传** `x-<prefix>-device-id`/`x-ds-platform`/UA；不要让中继自己编一套 |
| **`nonce` 重放** | `/oauth/get_token` 的 nonce 是一次性的 | 一次性使用，失败即重新走流程；不要把 nonce 落盘复用 |
| **新账号触发补绑手机** | 微信首登可能返回 `NEED_BIND_MOBILE` | UI 要有 **「需绑定手机号」** 分支提示，不可静默失败 |
| **出口 IP 不可信** | 代理/VPN 下仍可能吃 `RISK_DEVICE_DETECTED` | 复用**同一份**可操作文案（引导用户先用浏览器在同网络登录一次）；**不要**为扫码路径另写一套说辞 |
| **二维码/配对码被截图盗用** | 短码被他人看到可抢先绑定 | `user_code` 有效期短（≤5min）、一次性、绑定后立即失效；`device_code` 不显示给用户 |

### 7.3 ★ 一条硬纪律

> **任何网络操作都必须有失败出口。** 扫码轮询同样适用 ——
> 必须有总时长硬上限 + 明确的终止 UI（继承 Bug 17 的看门狗思路）。
> 「转圈没反应」是本项目用户明确表示**不可接受**的体验。
