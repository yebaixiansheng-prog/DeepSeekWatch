# DeepSeek 手表端 — 打包交接说明

> 面向：负责把它打包成华为 HAP/APP 格式并安装到手表的下一位 AI / 开发者
> 工程根目录：`DeepSeekWatch/`

---

## 一、这是什么

一个**华为鸿蒙智能手表（圆形表盘）上的 DeepSeek 客户端**。
纯原生 ArkTS 实现，不套 WebView，直接调用 DeepSeek 官方 Web API。

- 设备类型：`wearable`
- 语言：ArkTS（Stage 模型）
- 最低 API：**12**（JSON 配置声明）；**表冠功能需 API 18+**
- 包名：`com.dswatch.round`

---

## 二、打包步骤（DevEco Studio）

1. **打开工程**
   DevEco Studio ≥ 5.0 → `File > Open` → 选择 `DeepSeekWatch/` 目录（**不是** `entry/`）

2. **配置 SDK**
   `Settings > SDK Manager` → 勾选 `HarmonyOS SDK` → 安装 **API 12 及以上**
   若要启用表冠，建议 API 18+

3. **确认设备类型**
   `entry/src/main/module.json5` 中 `deviceTypes: ["wearable"]` 已是正确值，无需改动。

4. **签名**
   `File > Project Structure > Signing Configs` → 勾选 `Automatically generate signature`
   （需登录华为开发者账号）

5. **构建 HAP**
   `Build > Build Hap(s)/APP(s) > Build Hap(s)`
   产物：`entry/build/default/outputs/default/entry-default-signed.hap`

6. **安装到手表**
   ```bash
   hdc install entry-default-signed.hap
   ```
   或通过 DevEco Studio 的 `Run` 直接部署。

## 四、必须知道的几个关键点

### 1. 密码登录不需要人机验证 ✅

实测抓包确认：`POST /api/v0/users/login` 直接返回 token，**无任何验证码**。
所以工程里**没有**验证码 UI，这是有意为之，不要"补"上去。

### 2. 对话必须先过 PoW 工作量证明 ⚠️

DeepSeek 在 `/api/v0/chat/completion` 前强制校验 PoW：

```
POST /api/v0/chat/create_pow_challenge  {"target_path":"/api/v0/chat/completion"}
  → 返回 {algorithm, challenge, salt, difficulty, expire_at, signature}

本地对 nonce 递增计算 SHA3-256(salt + "_" + nonce)，
直到哈希满足 difficulty，然后：

请求头 X-<PREFIX>-PoW-Response = base64(JSON{algorithm,challenge,salt,answer,signature,target_path})
```

**本工程已完整实现**（`PowSolver.ets` + `Sha3.ets`），SHA3-256 已通过标准测试向量验证。

> ⚠️ **性能提示**：纯 TS 的 BigInt 实现比 WASM 慢。若手表端实测 PoW 耗时过长
> （>5 秒），可考虑：
> - 用 Native C++（NAPI）实现 Keccak，或
> - 编译官网的 `sha3_wasm_bg.7b9ca65ddd.wasm` 并用 `@ohos.web.webview` / WASM 引擎加载
> - 当前实现已做「分片让出主线程」，不会卡死 UI

### 3. 表冠事件 API 是 `onDigitalCrown`（不是 onAxisEvent）

```typescript
.focusable(true)
.defaultFocus(true)
.focusOnTouch(true)
.onDigitalCrown((event: CrownEvent) => {
  // event.degree: 相对旋转角度 [-360,360]，正=顺时针
})
```

- **仅 Wearable 支持**，API 18+
- 组件必须获焦才能收到事件
- `Scroll`/`List`/`Slider` 等**默认**已支持表冠滚动

本工程表冠行为：
| 页面 | 表冠作用 |
|---|---|
| 登录页 | 调节字号（小/标准/大） |
| 对话页 | 翻动上下文（滚动消息） |

### 4. 圆形表盘适配

- 所有页面最外层都加了 `.borderRadius('50%').clip(true)`
- 几何计算集中在 `RoundScreen.ets`，含安全半径、逐行宽度计算
- 字号集中在 `Typo`，三档可调，基准 14fp（手表规范 12-14fp）

### 5. 模式说明（重要，与官网现状对齐）

你提到的"快速模式/专项模式融合"，实测确认属实：

| 服务端 model_type | 状态 |
|---|---|
| `default`（快速模式） | ✅ enabled |
| `expert`（专家模式） | ❌ disabled |
| `vision`（识图模式） | ❌ disabled |

**处理方式**：本工程把「快速模式 / 专项模式」作为**表冠本地交互分层**实现，
两者共用 `model_type=default`，差异体现在默认参数：
- 快速模式：用户可自由开关深度思考/联网搜索
- 专项模式：强制默认开深度思考 + 联网搜索

识图模式按你要求**不做**（手表无法上传图片）。

### 6. 默认设置

| 项 | 默认值 |
|---|---|
| 深度思考 | **开**（`thinking_enabled: true`） |
| 联网搜索 | **开**（`search_enabled: true`） |
| 字号 | 标准 |
| 模式 | 快速模式 |

## 四点五、协议层易错点（改代码前务必看）

这几条都是实测踩出来的，**不知道就会写出能编译但跑不通的代码**：

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | `role` 大小写 | 服务端是 **`USER` / `ASSISTANT`（大写）**。按小写比较会让气泡对齐全错 |
| 2 | 消息完成状态 | 是 **`"FINISHED"`**，不是 `"OK"`（`OK` 只是 TS 枚举名，序列化用了 `FINISHED`） |
| 3 | `SEARCH` vs `TOOL_SEARCH` | **两个不同类型**。`SEARCH.content` 是可读文本；`TOOL_SEARCH.content` 是结构化 `queries/results` |
| 4 | 历史消息结构 | `chat_messages` 是**扁平数组 + `parent_id` 树**，直接按顺序渲染会乱序/重复 |
| 5 | 历史接口方法 | `history_messages` 是 **GET，查询参数在 URL query**（不是 POST body） |
| 6 | PoW 难度判定 | 取摘要**前 3 字节**（24 位）≤ difficulty。用前 4 字节会慢约 300 倍 |
| 7 | 会话前置 | 首次对话必须**先调 `chat_session/create`**，`chat_session_id` 传空串会报错 |
| 8 | SSE 事件作用域 | `event:` 只对**紧随其后的一帧**生效，不能跨帧复用 |

> 第 1、2、3、4 条是本轮代码审查中实际修掉的 bug，都写进了 `API_SPEC.md` 第 8、9 节。

### 关于「停止生成」的正确顺序

```
1. 先把本地消息标记为结束（清 streaming，把 WIP 片段置 FINISHED）
2. 再调 chat.stop() 中断 SSE + 通知服务端
```
反过来的话，SSE 在中断前还会灌进几帧内容，用户会看到"点了停止还在打字"。

## 六、已知限制

1. **沙箱环境无法端到端验证登录**：DeepSeek 对境外 IP 返回 `RISK_DEVICE_DETECTED`，
   需在真机（国内网络）验证。
2. **PoW 性能未在真机实测**：纯 TS SHA3 在手表 CPU 上可能较慢，见上文提示。
3. **未做会话列表页**：当前只保留"最后会话 + 新对话"，按手表屏幕尺寸做的取舍。
   如需历史会话列表，可调用 `/api/v0/chat_session/fetch_page`。
4. **`model_type` 仅支持 default**：官网 expert/vision 已下线，未来若恢复可扩展。

## 七、给下一位 AI 的建议

代码里凡是标了 **★** 的文件都是核心逻辑，改之前先读 `docs/API_SPEC.md`。
特别是：
- `Constants.ets` 里的所有接口路径、枚举值都来自实测抓包，**不要凭记忆改**
- `Sha3.ets` 已通过标准测试向量，**改之前先跑一遍 `""` 和 `"abc"` 的验证**
- `PowSolver.ets` 的 header 名是 `X-<PREFIX>-PoW-Response`（大写 X、DS），改错会导致对话 400
- `ChatPage.sendMessage()` 的步骤顺序（算 parentId → 建会话 → 追加消息 → 发请求）不能调换

**改动后的自检清单**：
1. 所有 `.ets` 括号配对
2. 具名 import 的名字在目标文件里确实 `export` 了
3. 没有引入未使用的 import（ArkTS 编译器会告警）
4. `struct` 的 `@State` / `@Prop` / `@Link` 全部声明在 `build()` **之前**
5. `ChatService.parseMessage()` 的 role 比较用 `Role.USER` / `Role.ASSISTANT`（大写）
