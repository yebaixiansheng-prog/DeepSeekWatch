# 官方 API 架构（v2 · 2026-09-30 推倒重来）

> 本文档描述**当前生效**的架构。
> v1（网页版逆向）的全部代码已删除，备份在 `legacy_backup/`（不进 git），
> 历史说明见文末「附录：为什么放弃 v1」。

---

## 1. 一句话

从「逆向 <API_HOST> 的私有协议」改为「调用 `api.<PROVIDER_DOMAIN>` 官方开放平台」。

| | v1（网页版逆向） | v2（官方 API，当前） |
|---|---|---|
| 端点 | `<API_HOST>/api/v0/*` | `api.<PROVIDER_DOMAIN>/chat/completions` |
| 鉴权 | 账号密码登录拿 token + **PoW 反爬** + 设备指纹 | **一个 API Key**（Bearer） |
| 反爬 | 必须算 PoW（`X-<PREFIX>-PoW-Response`），删了直接 40301 | 无 |
| 风控 | `RISK_DEVICE_DETECTED`，`device_id` 必须持久化 | 无 |
| 流格式 | 私有 SSE 帧 + `message_id` 去重 + `stop_stream` | **标准 OpenAI SSE**，`data: {...}` / `data: [DONE]` |
| 鉴权失败 | **恒 HTTP 200**，只能看 body 里的 `code` | **明确的 HTTP 401/402/429** |
| 会话列表 | 服务端有（`chat_session/*`） | **无**，必须自己存 |
| 联网搜索 | 服务端内置 | **无**，用 function calling + 客户端抓取实现 |
| 代码量 | ~7000 行（含 412 行哈希 + C++ NAPI） | ~2000 行，**纯 ArkTS** |

**收益**：删掉了一整类「协议被改就失效」的脆弱逻辑（PoW 算法、帧格式、风控指纹），
从 7000 行降到约 2000 行，构建产物从 1.6MB 降到 195KB，且不再需要 C++ 原生模块。

## 2b. ★ 人设（Persona）—— 2026-10-03 新增

### 2b.1 用户选定的设计

| 决策点 | 选择 | 影响 |
|---|---|---|
| 作用域 | **每个对话独立绑定** | 人设 id 挂在 `Session` 上，不是全局设置 |
| 字段 | **纯自定义，四个自由文本框** | 性格 / 背景 / 语气 / 回复风格，无预设模板 |
| 导航 | **独立页面 + 圆环菜单** | `PersonaPage` + `RadialMenu` |
| 圆屏 | **宽度全部按 y 计算** | 去掉所有字面百分比 |

### 2b.2 唯一注入点

```
doSend()
  → trimForSend(s.messages)          // 裁剪真实对话
  → 过滤空 assistant 占位
  → injectSystem(apiList, prompt)    // ★ 附加人设包装层
  → validateApiSequence(finalList)   // 校验（在注入**之后**）
  → api.chat({ messages: finalList })
```

**顺序纪律：必须先 `trimForSend` 再 `injectSystem`。**

反向（先注入再裁剪）在当前实现下**结果相同** —— `trimForSend` 规则 1
明确让 system 不占配额 —— 但那是**依赖内部实现细节**。先裁后注入
不依赖任何细节，语义也更清楚：「裁剪的是真实对话，人设是发送时附加的包装层」。

**空 prompt 不注入**：`injectSystem` 收到空串/纯空白会**原样返回**，
保证老会话（无 `personaId`）的行为与升级前**逐字节一致**。
这一点有测试锁住（14.10 / 14.11）。

### 2b.3 system prompt 为什么是结构化的

四个字段拼成**带标签**的 prompt，而不是串成一段散文：

```
你现在扮演的角色是「严谨助手」。

## 性格
沉稳、直接

## 背景
十年经验的资深工程师

（……语气、回复风格同理……）

## 通用要求
- 始终以该角色的身份和口吻回答，不要跳出角色。
- 不要提及你是「按设定扮演」，也不要复述上述设定内容。
- 如果设定与用户当前的明确要求冲突，以用户的当前要求为准。
```

- **结构化标签**让模型的遵循度明显更高 —— 它把每个 `## xx` 当独立约束，
  而散文里混着四个要求时，模型经常丢掉后面的。
- **尾部「通用要求」不是装饰**：不写它，模型被追问「你是不是 AI」时会出戏；
  「不要复述设定」能防止模型把 `personality` 原文念给用户 ——
  这是人设功能最常见的翻车点。
- **空字段整段省略**，绝不产生「性格：无」这种占位 ——
  那会让模型真去演一个「性格无」的角色。

### 2b.4 关键实现细节

| 点 | 做法 | 为什么 |
|---|---|---|
| id 生成 | `'p' + Date.now() + '_' + PersonaSeq.n` | ★ 只用时间戳时，**同毫秒连建**会得到相同 id → 第二次 save 被当成更新 → 用户看到「点新建没反应」。这是测试抓出来的真实 Bug |
| 向前兼容 | `str(o['personaId'])`，缺失即空串 | 老会话/老索引没有这个键，不能因此读不出来 |
| 索引冗余 | 索引里也存 `personaId` | 历史列表要在**不加载消息体**的前提下显示人设，否则打开列表页要读 30 份 JSON |
| 换绑 | `setPersona()` **不清空历史** | 人设是发送时的包装层，历史没被它改写过。清空只会让用户觉得「换个人设把我聊天记录弄没了」 |
| 换绑提示 | `needsFreshSession(old, new)` | **只有新老两边都填了设定**才建议开新对话（历史里有旧口吻的回答会打架）。「没人设→绑上」是升级，不该提示 |
| 不可变更新 | `withField()` 返回新对象 | ArkUI `@State` 只在引用变化时通知，从数据层杜绝原地改 |
| 跳转回传 | `Keys.PENDING_PERSONA`，读走**立刻清掉** | `router.back()` 不支持带参。不清的话下次进对话页会再次应用同一选择 |

### 2b.5 编辑页与全屏输入法

本机输入法是 `[0,0][466,466]` 的**全屏窗口，完全盖住 App**。因此编辑页：

- 显示态用 `Text`（不是常驻 `TextInput`）—— 5 个常驻输入框会各自渲染光标并抢焦点；
- 点击 → `beginEdit` → 主动 `focus()` 拉起输入法；
- **`onBlur` 必须结算字段**（`commitField`）—— 用户按系统 Back 收键盘时
  blur 一定会触发，这是唯一可靠的收尾时机；
- **绝不放「收起键盘」按钮** —— 它会被输入法盖住，既看不见也点不到（加过、验过、已删）。

## 2c. ★ 圆环径向菜单（导航）

### 2c.1 为什么圆屏要用径向菜单

传统顶部/底部导航条在圆屏上必然吃亏：

- 顶部一条 bar 占掉最金贵的纵向空间（升级前是 38vp，改菜单后对话区多出约 50px ≈ 一行半文字）；
- 底部一条 bar 落在 y≥450 的系统手势区，可点高度只剩 ~30px，必然误触。

径向菜单把**导航本身**放进圆里，天然贴合屏幕形状。

### 2c.2 布局不是图形学，是「一圈按钮 + 中心按钮」

不用 Canvas/Path 画扇形（圆屏小、抗锯齿差、还要自己做触摸），而是：

- 菜单项是 **54×54vp 的圆角方块**，放在角度 `centerAngleOf(i,n)`、半径 `56vp` 处；
- 交互用普通 `onClick`，命中判定交给 ArkUI；
- 环上最低点 = 233+112+58 = **403px < 436**（手势区硬上限）✅ 底部菜单项可点。

### 2c.3 ★ 判定与渲染必须共用同一套角度基准

角度约定：**0° = 正上方，顺时针递增**。

```
angleOf(dx, dy) = (atan2(dy, dx) * 180/PI + 90 + 360) % 360
```

`RadialHit.centerAngleOf` 同时用于**渲染摆位**（`offsetOf`）和
**表冠选中**（`feed`）。若两者各写一份 `cos/sin`，就可能漂移 ——
而漂移的表现正是「按钮画在这里，点上去却选中隔壁」，最难受也最难查。
测试 15.16 用「中心角 → 坐标 → 命中回同一扇区」（3~8 项全覆盖）把这条锁住。

### 2c.4 ArkTS 的 `.offset()` 陷阱（★ 两条错误夹出来的写法）

```ts
// ❌ Type '{ x: number; y: number; }' is not assignable to type 'Offset'
.offset({ x: dx, y: dy })

// ❌ Expected 1 arguments, but got 2   ← 这版 SDK 只有一个重载
.offset(dx, dy)

// ✅ 显式标注成内置的 Position 类型
private posOfIndex(i: number): Position {
  const p: Position = { x: x, y: y };
  return p;
}
.offset(this.posOfIndex(i))
```

**教训**：ArkTS 不是「更严格的 TS」，而是**另一套类型系统**，
重载解析规则不同。遇到这类报错要去看 SDK 的类型声明，不要靠 TS 的经验猜。

## 2d. ★ 圆屏几何（按 y 计算，不写死百分比）

### 2d.1 弦宽公式（权威）

466×466 圆，圆心 (233,233)，R=233。任一高度 y 处的弦宽：

```
halfW(y) = sqrt(R² - (y - 233)²)
```

关键点（px）：

| y | 物理弦宽 | 安全弦宽（R×0.88） |
|---|---|---|
| 233（圆心） | 466 | 410 |
| 350 | 403 | — |
| 415 | 291 | 189 |
| **428** | **255** | 127 |
| 436（硬上限） | 229 | 58 |
| 450（手势区起点） | 170 | 0 |

> ★ y=428 原先手抄成 **262**，实际是 **255**。7px 误差在「按钮放不放得下」
> 的判断上足以翻盘。**纪律：圆方程才是权威，手抄的实测值不是** ——
> 凡拿实测值当断言，先跑一遍 `2*sqrt(R²-(y-233)²)` 对账。

### 2d.2 三个边界

| 常量 | 值 | 含义 |
|---|---|---|
| `safeBottomPx` | 436 | **硬上限**：越过就被系统手势抢走 |
| `comfortBottomPx` | 415 | **舒适线**：推荐值，比硬上限更值得守 |
| `gestureTopPx` | 450 | 手势区起点，不作为可点区域 |

为什么硬上限之外还要一条更严的舒适线：安全圆在底部收拢极快 ——
y=415 安全弦宽还有 189px，y=436 只剩 58px。
**硬上限只是「不会被抢走」，不代表「那里放得下东西」。**

### 2d.3 两条渲染纪律

1. **宽度百分比必须 `Math.floor`，不能 `toFixed(0)`** ——
   四舍五入会让实际宽度**超出**可用宽度约 2px，在圆屏顶部足以切掉卡片边角。
   宁可窄 1%，也不要宽到被裁。
2. **整块区域取「最窄处」宽度**（`blockPct`）——
   一个卡片从 y=380 延伸到 y=440，它在 440 处最窄。
   按顶部宽度渲染会让底部两角被切掉。

## 3. 协议要点（全部实测确认）

### 3.1 请求

```
POST https://api.<PROVIDER_DOMAIN>/chat/completions
Authorization: Bearer <API_KEY>
Content-Type: application/json
```

请求体关键字段（`ApiClient.buildBody`）：

```jsonc
{
  "messages": [ {"role":"user","content":"..."} ],
  "model": "deepseek-flash",          // 或 deepseek-v4-pro
  "stream": true,
  "thinking": { "type": "disabled" }, // ★ 必须显式传，见 3.3
  "max_tokens": 4096,
  "tools": [ /* 仅开启联网搜索时 */ ],
  "tool_choice": "auto"
}
```

### 3.2 模型

| ID | 说明 |
|---|---|
| `deepseek-flash` | 默认。响应快 |
| `deepseek-v4-pro` | 能力更强 |

### 3.3 ★★ 最大的坑：`thinking` 省略 = 默认**开启**思考

实测（2026-09-30）：

```bash
# 不传 thinking，max_tokens=10
{"messages":[{"role":"user","content":"hi"}],"model":"deepseek-flash","max_tokens":10}
# → content: ""  ← 空的！
# → reasoning_content: "The user just said \"hi\". I should respond"
# → finish_reason: "length"  ← 10 个 token 全花在思考上
```

**手表场景下这是致命的**：用户会盯着一个空白的转圈等很久。
所以 `buildBody` **无条件**输出 `thinking` 字段，关闭时传 `{"type":"disabled"}`。

> 纪律：**任何依赖服务端默认值的字段，都必须显式传。**
> 默认值会变，而「省略」这个行为在代码里看不出来。

### 3.4 流式响应（标准 OpenAI 格式）

```
data: {"choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":null}]}
data: {"choices":[{"index":0,"delta":{"content":"好的"},"finish_reason":null}]}
data: {"choices":[{"index":0,"delta":{"content":"，"},"finish_reason":null}]}
...
data: {"choices":[{"index":0,"delta":{"content":""},"finish_reason":"stop"}],"usage":{...}}
data: [DONE]
```

要点：
- 首帧 `delta` 里只有 `role`，`content` 是**空串**；
- 尾帧 `content` 也是空串，但 `finish_reason` 非 null，`usage` 挂在这一帧上；
- 思考模式下 `delta.reasoning_content` 先于 `delta.content` 到达；
- 结束标记是 `data: [DONE]`。

### 3.5 错误码（比 v1 好处理得多）

| HTTP | 含义 | 应用文案 |
|---|---|---|
| 401 / 403 | 密钥无效 | 「API 密钥无效，请在设置里重新填写」 |
| 402 | 余额不足 | 「账户余额不足，请先充值」 |
| 429 | 限流 | 「请求太频繁，请稍后再试」 |
| 5xx | 服务端故障 | 「DeepSeek 服务暂时不可用，请稍后重试」 |
| 0（网络层） | 不通/超时 | 「网络不通，请检查手表 Wi-Fi」 |
| 其它 4xx | 有 `error.message` 就用它 | 否则「请求失败（HTTP xxx）」 |

> 纪律：**这六种文案必须互不相同**。有专门的测试断言这一点
> （`tools/api-protocol-test.mjs` 的 `D 六种错误文案互不相同`），
> 因为「把两种错误写成一句话」是极易犯、又极难被用户说清的错。

## 4. ★ 联网搜索（function calling + 客户端抓取）

用户原话：「联网搜索功能，你看看能不能想一下办法做一下，实在不行就算了。」
结论：**能做，且不需要任何第三方 API 密钥。**

### 4.1 为什么不能直接搜

DeepSeek 官方 API **没有**内置联网搜索（v1 网页版有，但那是服务端能力）。

### 4.2 做法：把搜索实现成 function tool

```
① 请求带 tools 声明
      ↓
② 模型判断需要实时信息 → 返回 tool_calls
   {"name":"web_search","arguments":"{\"query\":\"今日科技新闻\"}"}
      ↓
③ 【客户端】抓 Bing 搜索结果页 → 解析出标题/链接/摘要
      ↓
④ 把结果作为 role:"tool" 消息追加，再请求一次
      ↓
⑤ 模型基于真实搜索结果作答
```

已实测跑通（`tools/live-e2e.mjs` 第 4 节），真实输出示例：

```
模型要搜: 今日科技新闻
取到 10 条，首条: 科技新闻_央视网 (cctv.com)
最终回答: 据 Readhub 每日早报（12小时前），今天的科技热点包括 OpenAI 因数据泄露解雇三名安全研究员…
```

### 4.3 搜索源选型（2026-09-30 实测）

| 源 | 结果 |
|---|---|
| DuckDuckGo（`lite.duckduckgo.com` / `api.duckduckgo.com`） | ❌ **直连超时**（HTTP 000，20s 无响应） |
| **Bing 中文站**（`cn.bing.com/search`） | ✅ **HTTP 200，97KB 真实结果页，`<li class="b_algo">` 结构稳定** |
| 百度 / 搜狗 | ⚠️ 可返回 200，但反爬更激进，未启用 |

### 4.4 解析的脆弱性（必须正视）

`parseBing` 依赖**第三方页面的 HTML 结构**，脆弱是本质的。因此：

- 解析失败的判据是「条目数为 0」，**不是抛异常**；
- 返回 0 条时，`formatForModel` 会生成一段**明确指示模型不要编造**的文本：
  ```
  【联网搜索：未找到"xxx"的结果】
  （搜索源未返回可用条目，可能被限流或改版。请如实告知用户你没能检索到实时信息，不要编造。）
  ```
- **搜索失败绝不允许升级成「整个回答失败」** —— 对话必须继续。

> 纪律：**「未配置」「网络失败」「搜到 0 条」是三种不同的状态，不许复用同一句话。**
> 对应地，`SearchService.search()` **永不抛异常**，失败也返回 `ok:false` 的结果对象。

### 4.5 轮数上限

`SearchConfig.MAX_ROUNDS = 2`：防止模型陷入「无限调工具」死循环。
超限时明确报错「模型请求联网搜索，但搜索不可用或已达上限」，而不是静默返回空回复。

## 5. ★ 上下文裁剪与序列校验

### 5.1 为什么要裁剪

官方 API 是**无状态**的：每次请求都要自带完整 `messages`。
手表上下文有限、网络慢，必须只发最近 N 条（`MAX_SEND_MSGS = 24`）。

**裁剪只影响发送，不删本地历史** —— 用户往回翻还能看到完整记录。

### 5.2 裁剪不能破坏的配对关系

官方 API 对消息序列有硬约束：

```
assistant(tool_calls=[c1])  ←→  tool(tool_call_id=c1)
```

一旦裁剪把配对切散（留下 tool 却切掉了它的 assistant），服务端只会回一个 400，
用户看到的是「莫名其妙失败」。

`trimForSend` 因此必须：
1. 保留第一条 `system`；
2. 起点若落在 `tool` 上 → **往前回溯**到发起它的 `assistant`；
3. 末尾若是「声明了 tool_calls 却缺结果」的 `assistant` → 裁掉。

### 5.3 `validateApiSequence`：结构不变量校验

除了裁剪，还提供**独立的校验器**，发送前跑一次：

```ts
const errs = validateApiSequence(apiList);
if (errs.length > 0) {
  // 明确告知 + 放弃本轮（不静默降级、不发出坏请求）
  this.errMsg = '对话上下文异常，请开启新对话';
  return;
}
```

校验的不变量：
- 首条不能是 `tool`；
- 每条 `tool` 必须能按 id 追溯到**前面**的 `assistant.tool_calls`；
- 每条 `assistant.tool_calls` 必须收到对应结果（末尾悬挂视为非法）；
- `tool` 消息必须有 `toolCallId`。

> ★ 这个校验器同时是**测试的断言依据**。
> 断言「结构不变量」比断言「某个具体下标的值」强得多：
> 前者能抓住整类 bug，后者只能抓住你恰好想到的那一个实例。

## 6. 本地会话存储

官方 API 无云端会话，历史全部本地存（Preferences）。

```
Keys.SESSION_INDEX   → 会话索引 JSON（id/title/createdAt/updatedAt/count/personaId）
session_<id>         → 单条会话的消息体 JSON（含 personaId）
Keys.LAST_SESSION    → 最近打开的会话 id（冷启动恢复）
Keys.PERSONA_LIST    → 人设列表 JSON
Keys.LAST_PERSONA    → 上次新建对话选的人设 id（作为下次默认）
Keys.PENDING_PERSONA → 跨页回传（人设页 → 对话页），读走即清
```

上限：单会话 200 条（`MAX_STORED_MSGS`）、最多 30 个会话（`MAX_SESSIONS`）、
最多 20 条人设（`MAX_PERSONAS`），会话超出按「最久未更新」淘汰。

**索引损坏时的行为**：重置为空列表，而不是让应用崩掉 ——
用户最多丢列表（消息体仍在磁盘上）。人设列表损坏同理，降级后种入默认项。

★ **索引缓存失效**：`ChatStore.index()` 有内存缓存（`loaded` 标志）。
跨页返回时必须 `ChatStore.invalidate()` 再读，否则拿到的是上一份快照 ——
表现为「刚聊完的对话，回历史列表看到的还是旧标题」。
`PersonaStore` 用同一个模式（`invalidate()`）。

## 7. 离线验证体系

> 核心理念（来自 `skills/offline-regression-testing`）：
> **测试质量 = 交付质量**。手表上验证一轮要 3~5 分钟，
> 协议层的问题必须在 PC 上几秒钟验证完。

### 7.1 `tools/ets-load.mjs` —— 通用 .ets 加载器

把 `.ets` 机械剥离类型后当 ES module 跑，**不重写逻辑**。
这样测的是**真源码**，不是副本。

> 历史教训：曾「手抄」一份 PoW 算法来验证，抄错 5 处高低位顺序，
> 得出「工程算法有问题」的**错误结论**，白排查很久。

**内置安全网**：剥离后立刻做语法检查（`new Function`），
一旦非法就抛错并指出生成源码 —— **绝不把变异过的副本喂给测试**。

> ★ 剥离规则的两个坑（都真踩过）：
> 1. `extractBlock` 做括号配平时**必须先剔除注释**。本工程 JSDoc 里大量出现
>    `{ ... }`，不剔除会导致配平**提前结束**，函数只剩签名 ——
>    而**空函数体语法合法**，测试会在「函数永远返回 undefined」的情况下跑绿。
> 2. 判据不能写 `head.includes('=')` —— 函数签名里的**默认参数**
>    （`max: number = 24`）也会命中，会把整个函数体丢掉。

### 7.3 `tools/mutate.py` —— 注入测试（★ 最重要）

```bash
python tools/mutate.py all      # 全部注入 → 跑测试 → 还原
python tools/mutate.py run 3    # 单条
```

**「从没红过的检查等于没有检查。」** 测试全绿可能是真的都对，
也可能是断言根本没覆盖到那条路径。唯一能区分两者的办法就是故意改坏。

26 个注入点，每个都对应一个**真实可能犯的错误**：

**协议层（10 个）**

| # | 注入 | 对应的真实风险 |
|---|---|---|
| 0 | 删掉 `thinking` 字段 | 省略=开启思考，首字延迟极长 |
| 1 | SSE 不认 CRLF | 部分服务端用 `\r\n\r\n`，整条流解析不出来 |
| 2 | SSE 不做跨块缓冲 | HTTP 分块边界会切碎 JSON |
| 3 | 工具参数覆盖而非累加 | `arguments` 是分片下发的 |
| 4 | 鉴权失败复用网络文案 | 用户不知道该做什么 |
| 5 | `reasoning` 回传给 API | 官方 API 不接受，会 400 |
| 6 | 裁剪不回溯 tool 配对 | 产生孤立 tool → 400 |
| 7 | 裁剪不处理悬挂 tool_calls | 工具结果没回来就发出去 → 400 |
| 8 | 校验器对孤立 tool 视而不见 | 把校验器废掉 |
| 9 | 解析器不校验链接 | 把导航栏当成搜索结果 |

**人设 + 圆屏（16 个，2026-10-03 新增）**

| # | 注入 | 对应的真实风险 |
|---|---|---|
| 10 | 空 prompt 也注入 system | 老会话行为变化（升级前逐字节一致性被破坏） |
| 11 | `injectSystem` 改入参 | 调用方拿到的数组被偷偷改了 |
| 12 | 拼 prompt 时漏一个字段 | 用户填了却没生效 |
| 13 | 空字段不省略 | 出现「性格：无」，模型真去演"无性格" |
| 14 | id 只用时间戳 | 同毫秒连建撞号 → 「点新建没反应」 |
| 15 | 老会话 `personaId` 硬取 | 升级后老会话直接读不出来 |
| 16 | 宽度百分比忽略 y | 回到写死 86%，圆屏底部被圆弧切掉 |
| 17 | 安全圆系数不生效 | 用物理半径当安全半径，底部元素越界 |
| 18 | 极角不归一化 | 3 点钟方向得 -270°，扇区判定全错 |
| 19 | 角度基准错 90° | 以 3 点钟为 0° → **点上方选中右边那项** |
| 20 | 命中判定忽略环形约束 | 圆心附近也算命中，中心按钮抢不到点击 |
| 21 | `offsetOf` 与 `angleOf` 不互逆 | 菜单画的位置与判定角度对不上 |
| 22 | 表冠在菜单收起时也生效 | 改到用户看不见的选中项 |
| 23 | 换人设时清空历史 | 用户觉得「换个人设把我聊天记录弄没了」 |
| 24 | 换人设无脑建议开新对话 | 连「没人设→绑上」这种升级场景也提示 |
| 25 | 索引不冗余存 `personaId` | 历史列表要加载全部消息体才知道人设 |

> ★★ **这套注入测试真的抓到了漏洞（2026-09-30）**：
> 注入 6 最初**未被捕获**。排查发现 `trimForSend` 的回溯分支
> **从没被执行过** —— 当时用例 `max=3` 的裁剪落点恰好是 `assistant`，
> 绕过了 `while (role === TOOL) start--`。
> 也就是说：**代码是对的，但「它对的证据」是假的**。
>
> 修法不是把 `max` 改对就完事，而是：
> ① 把校验逻辑抽成独立的 `validateApiSequence`；
> ② 测试改成断言**结构不变量**，并对**所有 max 取值**穷举验证（E7/E8）。
> 这样能抓住整类 bug，而不是某一个实例。

> ★★ **它又抓到了一个（2026-10-03）**：注入 25 最初**未被捕获**。
> 排查发现 16.2 看似在测「新增索引项」分支，实际测的是「更新」分支 ——
> 因为 `create()` 内部已经 `save()` 过一次，索引缓存里已有这条，
> 后面那次 `save()` 走的是更新路径，**`idx.push` 那行从没被执行**。
>
> 这正是注入测试的价值：**它发现了 16.2 只测了一半**。
> 修法是把两条分支**各自用干净状态**测（新增分支需要同时
> `__resetMem2()` **和** `invalidate()` —— 只清 kv 清不掉内存缓存），
> 并补上「换绑后索引要同步」的断言（16.6c）。
>
> ★ 纪律：**`__resetMem2()` 清的是底层 kv，清不掉 `ChatStore` 的内存缓存**；
> 凡是要测「首次写入」的用例，必须同时 `invalidate()`。

**两条写圆屏断言时的纪律**（都真踩过）：

1. 断言里 `rowPct` **不能要求「逐行不增」** —— 长列表跨越圆心时，

   「关于圆心对称」+「从中心向两端单调不增」。
2. 断言前**先确认单位**。曾把 `yVp` 又乘了一次 2，
   算出「可用 -24.0px」这种不可能的值 —— 是测试错了，不是源码错了。
   凡遇到「物理上不可能」的数值，第一反应应该是检查测试的输入。

## 8. 安全与发布

### 8.1 密钥是内置的

`Constants.ets` 的 `ApiKey.BUILTIN` 直接写了真实密钥（用户明确要求）。

**边界**：
- 该密钥**只能**用于个人自用构建产物；
- **绝不可**推到公开仓库 —— GitHub 上扫 `sk-` 前缀的爬虫是**分钟级**的，
  泄露后会被盗刷；
- `tools/desensitize.py` 在导出公开文档时做脱敏，
  但**代码文件本身不参与公开同步**。

### 8.2 如果要开源

必须先做：
1. 把 `ApiKey.BUILTIN` 改成空串，密钥改为运行时从设置页输入；
2. 或引入构建期注入（`build-profile` 里读环境变量）。

## 附录：为什么放弃 v1（网页版逆向）

v1 在技术上**是成功的** —— 它确实跑通了，包括：
PoW 计算（还写了 C++ NAPI 加速 190 倍）、私有 SSE 帧解析、
`message_id` 去重、`stop_stream` 清僵尸流、设备指纹持久化。

但它有三个**结构性**问题：

1. **脆弱**：依赖前端 bundle 的私有实现。上游改一个字段、换一次帧格式、
   加一道风控，整个应用就失效，且**没有官方文档可查**。
2. **复杂**：7000 行代码里，真正「聊天」的部分不到 1/5，
   其余全是在对抗反爬（PoW、指纹、UA、preempt 语义）。
3. **不可维护**：踩过的坑（`preempt` 必须 true、`message_id` 不能 static 去重、
   `device_id` 必须持久化…）全靠人肉积累，换个人接手几乎无法复现。

改用官方 API 后，这三条同时消失。

**保留 v1 备份的理由**：如果哪天官方 API 不可用，`legacy_backup/` 里是完整的
可回退实现（含 C++ 模块与全部测试）。它不进 git，只是本地保险。
